## 一、产品是什么

面向京东业务人员与本地安装服务商的充电桩安装信息管理平台。工作台 2.0 围绕 AI 能力重新组织业务交互：业务信息到达后系统主动完成适用的整理与分析，人员打开工作台优先看到需要自己核实、确认或处理的事项。

用户打开工作台 3 秒内能理解的三件事：

- 当前有哪些事项需要我处理？（待处理事项列表）
- 每个事项系统已经分析了什么、还缺什么？（分析结果与待核实问题）
- 我下一步该点哪里？（进入事项核实、确认、处理）

## 二、用户角色

角色与职责定义见 [BRD](../01-brd/BRD-jd-charging.md) §3.1 与 [术语表](../03-foundation/03-01-glossary/glossary.md) §3。命名以术语表为准。

| 角色 | 使用场景 |
|------|---------|
| 京东业务账号 | 统一处理安装核查、双方费用核对、履约协同与异常 |
| 服务商账号（每家公司一个） | 统一处理本公司接入配置、安装资料确认与提交、补充回复、应收查看与对账回复；只能访问所属公司的数据 |

权限全局约定：身份与业务权限由服务端核实，按动作与业务范围授权；前端不传身份参数、不做权限判断。深链接打开任何页面都执行身份范围检查。完整约定见 [公共约定](../03-foundation/03-06-provided-apis/common-contract.md)。

## 三、系统架构与全局设计原则

```text
┌──────────────┐   ┌──────────────────────────┐   ┌────────────────────┐
│ 浏览器工作台   │──→│ 本系统服务端（Hono Worker） │←──│ 后台任务程序（Node）  │
│ 纯渲染层      │   │ 权限/校验/计算/持久化/调度  │   │ OpenCode+业务Skill  │
└──────────────┘   └───────┬──────────┬───────┘   └─────────┬──────────┘
                           │          │                     │
                    ┌──────┴───┐  ┌───┴────────┐     结果校验后入库
                    │ 本系统D1  │  │ 外部依赖适配 │
                    └──────────┘  └───┬────────┘
                                      │
                          ┌───────────┴────────────┐
                          │ 模拟业务接口（mock 专题） │
                          │ 模拟来源数据与原始文件    │
                          └────────────────────────┘
```

**核心设计原则**（跨功能块成立，子 PRD 不重复）：

| 原则 | 含义 |
|------|------|
| 前端是纯渲染层 | 拿到什么展示什么，不做业务判断、不生成业务数据与成功结果 |
| 数据只来自本系统 API | 列表、详情、统计、证据、分析结果与操作结果全部经本系统 API 返回；禁止浏览器随机数、静态 JSON、localStorage 或请求拦截器代替 |
| 服务端真实处理 | 权限校验、转换、金额计算、事项创建、人工处理、持久化与状态流转均由服务端真实执行；写接口成功必须有实际状态变化 |
| 后台统一取数、固定版本 | 后台按事项读取其他系统并固定来源版本后交给 Skill；转换与确定性计算由程序执行，Skill 只做规则生成与证据判断 |
| 原记录归属不变 | 双方正式记录与账单保持原有归属；工作台辅助理解、核查与协作，业务决定由原责任人作出，AI 不自动批准费用、不改真实账单 |
| 写入有保护 | 提交按版本条件校验，重复请求按幂等标识去重，结果未知经回查确定，不盲目重写 |
| 失败真实呈现 | 接口失败、材料缺失、分析失败展示真实状态，不补造数据、判断或成功提示 |

### 5.2 接口调用时序

工作台初始化：先 `GET /api/admin/charging/session` 取得当前身份与业务权限，再按页面调对应读取接口。待处理事项页调 `GET /work-items/summary` 与 `GET /work-items`；详情页按事项类型调对应详情接口（草稿 / 核查 / 对账 / 配置 / 协同）。工单页调用 work-orders 列表/详情，关联事项按 workOrderId 过滤；对账列表直接使用 work-items 返回的 reconciliationSummary。完整读取链路见 [sys-workbench-read](../03-foundation/03-07-system-flows/sys-workbench-read.md)，分析准备链路见 [sys-analysis-preparation](../03-foundation/03-07-system-flows/sys-analysis-preparation.md)。

全部 38 条接口（含 7 条内部 SERVICE 路由）见 [本系统接口清单](../03-foundation/03-06-provided-apis/README.md)；前端只调用浏览器接口，内部路由由后台任务程序使用。

### 5.3 区域联动

- 人员完成提交、核查决定、补充、对账处理或协同操作后，对应事项状态与待处理列表同时更新，先骨架屏后替换渲染。
- 资料正式提交后由服务端自动产生后续核查事项；退回后的服务商回复继续原事项，不另建重复事项。
- 后台分析完成后事项中直接呈现分析结果，不要求人员逐项触发 Skill；分析失败以真实状态进入待处理（分析失败恢复场景）。

## 六、系统数据全景

```text
外部来源记录（工单/订单/材料/双方账单/条款）发生变化
    ↓
变化接收批次可靠接收并保存读取位置（execution 域）
    ↓
后台任务读取来源、固定分析输入快照；程序执行转换与确定性计算
    ↓
业务 Skill 形成整理、证据或解释结果，校验后入库（evidence 域）
    ↓
产生或更新处理事项，待处理列表呈现分析结果与待核实问题
    ↓
人员核实、确认、提交或处理（human_decision / activity_record）
    ↓
需写回来源的操作经外部业务写入登记并核实原系统结果
    ↓
处理记录与版本保留，供处理记录页与后续变化接续追溯
```

数据链路原则：每个子 PRD 注明数据从哪个接口取得、由谁计算、写入何处、处理后如何回查；模拟来源与本系统数据库分别管理，见 [运行数据规则](../../rules/runtime-mock-data.md) §2。
