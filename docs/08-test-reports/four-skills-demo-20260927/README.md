## 3. 修复的实际根因

| 所在位置 | 原问题 | 已实施修复 |
| --- | --- | --- |
| 来源数据生成 | 正常费用差异只改行金额，数量、单价不支持金额；有些跨工单账单缺少明确分摊，造成普遍缺依据 | 源数据共用业务事实，数量×单价与行金额保持一致；正常差异有合同/验收依据，明确缺资料另列负例 |
| 安装材料生成与输入 | 配置样表易被当成实际施工材料；图片真实画面不足，实际提取场景不完整 | 工单施工记录与配置样表分别保存；提供可读 PDF/图片；已启用同格式配置可用于真实工单 |
| 外部写入执行器 | 写入按只读后台主体执行，实际业务动作不能完成 | 按已保存的人工作业身份执行，服务主体继续只读，原权限边界保留 |
| 补充回复同步 | 使用旧快照或空的明细版本，回复附件只有编号未传实际内容 | 提交前重读当前工单/明细版本；上传字节、校验 SHA 后传入来源；回复可由京东重新读取 |
| 分析取数与核查要求 | 已提交回复未完整进入分析；方案、明细所属工单信息被丢失；把没有细分段号的普通项目强制判缺 | 新输入保存可靠回复与材料引用；保留并校验关联工单；按原资料粒度核查，仅在确实需要区分时要求段号 |
| 来源回传与本地结果接续 | 同一成功写入回传后重复生成事项，或旧通知再次打断当前结果 | 成功回执采用统一业务身份；精确识别同代已读取版本，真实新版本仍使原结论失效 |
| 前端展示 | 工程字段直接展示，上传与材料入口不明显 | 配置详情前置 Excel 下载/上传、原表及中文字段含义，转换值以表格呈现；原始记录放在可展开详情 |

## 5. 使用范围与角色走查

服务商的配置流程为上传→查看原表→运行→核对试转换→启用；安装流程为读取/上传→运行→核对草稿→提交。京东在同一工作台核查，缺材料时发起补充；服务商在原事项回复，京东重分析后确认。无需另到 mock 系统重复手工录入。

PDF/图片的识别文字须逐页由人核对后保存，再运行提取。当前提供的案例都是可读文字施工记录；现场照片、印章、图形等不能据此宣称已经具备完整视觉业务判断能力。未知字段含义和确实缺依据仍要求补充，不为演示强行生成通过结论。

业务对账完成分析只提供解释和核实入口。原账单未修订时继续显示真实差额，系统不自动付款，不伪造账单一致。
