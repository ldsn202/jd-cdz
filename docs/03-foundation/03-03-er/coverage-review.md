## 1. 核对范围与判据

核对当前 BRD、原型、术语表、十二份外部开发契约和七份 ER 图文。目标是确认现有业务范围可以据此继续设计业务流程，未把数据库、真实接入或运行测试算作 ER 完成证据。

| 范围 | 本次清单 |
| --- | --- |
| 关系分域 | 处理事项、材料证据、安装资料、对账、接入配置、身份责任、变化执行，共七份 |
| 图与关系 | 十八张图，三十九类不同实体，八十条图中关系；跨图重复展示的关系计入八十条，不等于八十条独立外键 |
| 命名 | 术语表 V1.11 共六十六项；三十九类图中实体均有定义，其他条目包括职责、状态、业务数量及 Skill 名称 |
| 必要约束 | 归属、版本、条件基数、人工确认、执行恢复和历史访问均在对应分域说明；实体清单不直接当作建表清单 |

## 2. 业务需求与交互覆盖

| 现有需求 | 由哪些关系承担 | 保留的业务约束 |
| --- | --- | --- |
| 打开工作台直接处理 AI 结果 | 变化 → 后台任务 → 固定输入与能力调用 → 分析 → 处理事项 | 后台主动准备，人员无需逐项选择 Skill 或发出分析指令 |
| 接入配置 Skill | 服务商 → 配置 → 候选版本；建议分析、试转换、人工启用和当前生效版本 | 人员确认含义与范围；已适用配置继续复用，不逐单重审 |
| 安装资料整理 Skill | 原材料与解析 → 分析 → 草稿及完整版本 → 人工决定 → 明细提交 | 人员核实事实并提交；AI 建议不直接变成正式明细 |
| 安装资料核查 Skill | 正式明细及证据 → 分析发现 → 证据引用 → 人工决定 | 找到材料不等于审核通过；正式决定由当前责任人作出 |
| 补充后接续原事项 | 原退回决定、补充回复、本次提交确认和执行结果 | 回复指向仍有效的原问题；成功后自动更新分析，不重复建事项 |
| 对账差异解释 Skill | 双方原账 → 固定比较 → 分组与费用依据 → 差异解释 → 核实问答 | 程序计算与 AI 解释分开，原账独立，核对一致不等于批准或付款 |
| 服务商修订本方应收 | 原应收读取、新版输入与原对账事项 | 修订仍在原系统，工作台不新增改账接口或京东代改步骤 |
| 履约协同与本地异常 | 事项责任、人员动作、实际结果及历史记录 | 可无 AI 分析；不套用安装审核通过动作；外部状态映射留业务流程核实 |
| 工单列表、事项详情与处理记录 | 工单与事项归属，分析、决定、回复、执行结果的时间视图 | 处理记录为既有事实的展示，不再造一套互相覆盖的业务结果 |
| 原文预览与历史追溯 | 输入项 → 解析块 → 解析及材料版本；记录字段引用实际保存内容 | 版本固定，历史与下载按当前权限；不能用最新材料替换旧依据 |
| 六类人员与后台程序 | 稳定身份、当次授权、当前责任和原确认人 | 角色名不等于具体人员；查看权限不自动包含材料、账单与办理权 |
| 读取失败、分析失败或提交结果未知 | 后台任务、执行尝试、能力调用与外部写入 | 按实际失败阶段恢复；已成功回复、确认或写入不要求重复办理 |

## 3. 外部输入与输出覆盖

| 开发契约 | 在 ER 中保存或引用的位置 | 范围检查 |
| --- | --- | --- |
| 安装工单上下文读取 | 工单、方案、正式明细及固定输入中的原内容 | plannedQuantity 与 installedQuantity 分开；当前记录及版本须可核实 |
| 原始材料读取 | 材料及确切版本，解析结果与输入引用 | 完整字节和摘要不替代来源版本；读取失败不伪装空文件 |
| 购买订单与安装权益读取 | 输入项内的 PURCHASE_ORDER / INSTALLATION_ENTITLEMENT 原内容及工单关联依据 | 只读源记录，不重建订单账本；权益上限、实际数量和费用分别处理 |
| 服务商资料与格式说明读取 | PROVIDER_RECORD / PROVIDER_FORMAT 输入项，以及材料版本 | 原说明、AI 建议和确认配置分开；无说明不补造格式版本 |
| 正式安装明细提交 | 人工决定、明细提交类型、稳定外部写入与正式明细回执 | 确认内容、submissionId 与成功版本一致；未知结果先回查 |
| 核查决定与补充同步 | 人工决定、补充轮次、外部写入与回执 | operationId 固定；更换 action 不绕过同号内容冲突 |
| 京东账单读取 | 京东账单、原分项、固定输入和本次比较 | 原总额、目标工单金额及分项分别保存，禁止猜测分摊 |
| 服务商应收读取 | 本方应收、原分项、确切新版及原事项 | 取得新版才能比较，不把人员答复当成新版原账 |
| 计费条款与批准记录读取 | 相关原记录、输入项、版本与证据引用 | 工单相关不等于具体费用适用；未取得与明确无记录分开 |
| 原记录变化发现 | 配置代次、接收批、稳定变化、可恢复任务和位置 | 同事务保存后推进，不凭空批声称来源全部同步 |
| 当前身份与业务权限取得 | 身份引用、当次上下文、授权项及原账号映射 | 历史授权只供追溯；新动作和异步新写出重新核实 |
| AI 推理与材料解析 | 固定能力调用、尝试、输入及采用结果 | 两种输入输出互斥；AI 可有限重试，结果发布仍检查当前版本 |

订单、权益、原格式说明等只读源内容由固定输入承载，不需要为读取副本重建一套业务管理关系。材料解析的页面、sheet、单元格位置，规则参数、计费范围、权限范围和回执内容采用所属实体的内部结构。表结构阶段必须保存这些内容，不能因未各画一张实体框而丢弃。

## 4. 跨域一致性核对

| 检查对象 | 总核对结论 |
| --- | --- |
| 一个事项的范围 | 限定一家服务商；安装相关事项关联工单，配置事项可无工单。来源关联未核实时保留待核实任务，不伪造工单 |
| 事项、输入与分析 | 分析、输入快照及实际调用的任务归属一致；每次采用结果绑定固定输入，旧结果不覆盖当前事项 |
| 配置与试转换 | 候选版本、试转换使用的版本、输入所属配置事项及启用确认一致。原建议分析保留原输入，试转换使用自己的确切输入 |
| 输入版本与实现版本 | 业务输入、Skill 规则、所用接入配置改变则新建快照及调用；仅模型实现变化可以复用未变业务输入，但必须新建绑定该实现的调用 |
| 业务子类型的必填关系 | 草稿提交、配置启用、费用问答等图中的人工决定均有明确适用子类型；不把某图条件强加给其他动作 |
| 历史导入与本地确认 | 原系统已有明细和决定可以没有本地草稿、分析或授权核验。保留来源与未知项，不补造本地历史 |
| 安装明细与统一写入 | 明细提交记录是同一外部业务写入的一种，保持一套确认内容、submissionId 与结果；不增加第二笔操作 |
| 补充与费用问答 | 安装回复关联原退回及本次提交；费用回复关联原费用问题和当时比较。两种业务不复用同一写接口 |
| 原账与比较范围 | 整单多工单关系不推导分项归属；本次比较固定原账版本，不改原总额；无分配依据时不猜金额 |
| 身份、责任与执行 | 本地人工决定保留原确认人；后台尝试保留实际程序。当前责任转交、撤权及重新核验不改写旧身份事实 |
| 变化、尝试与结果 | 收到变化、完成取数、采用分析、人员确认和源端写入成功分别判定。每个阶段失败都有原任务或原操作可继续 |
| 删除与访问 | 本期正常流程不级联删除已引用历史；保留历史不扩大访问权限，保存期限及合法删除仍需实施前确定 |

以上为设计一致性核对。实际原系统的版本、权限、条件写入与回查能力仍待提供方验证；文档中的约束不能代替运行证明。

## 5. 本轮修正

| 发现 | 已作修正 | 影响范围 |

| “换配置须换快照”未区分业务配置与模型实现 | 明确业务输入和实现配置的不同处理，保留新调用要求 | 材料与证据说明更新至 V1.1，基数不变 |

## 6. 阶段结论与下一步

ER 文档已完成范围与一致性核对，业务主流程与角色交接已形成：围绕人员收到什么结果、核实什么、作出什么决定，以及补充或异常后如何回到原事项，串起现有四类 Skill 的业务场景。

业务流程图保留业务角色、动作、判断及结果；接口、数据库和后台执行细节由后续系统流程承担。先完成主流程，再逐项展开资料整理、核查补充、对账、配置及共用异常，不同时编写所有功能规格。

后续必须落实：表结构中的唯一约束与版本保护、本系统接口的权限和状态条件、系统流程中的接收事务与恢复、PRD 的完整交互及验收标准。真实身份、来源覆盖、原记录字段与源端写入能力继续列为对接待核实项，不把 ER 文档完成写成产品或真实接入完成。
