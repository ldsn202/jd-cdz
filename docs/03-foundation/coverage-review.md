## 2. 业务覆盖走查

| 角色 | 从打开工作台到办理结束 | 后台替代的重复动作 |
| --- | --- | --- |
| 京东安装资料核查 | 查看当前证据与差异 → 通过或要求补充 → 原事项等待实际结果 | 自动取数、定位材料、准备判断与补充后的重新分析 |
| 服务商资料人员 | 核实草稿 → 修订或确认提交；退回后补充并提交 | 自动提取、转换和组织资料，无需逐项选择 Skill |
| 京东业务对账 | 查看程序比较与解释 → 对疑点发起核实或保存事实 | 自动匹配已确认关系、计算差额、读取新版并重新核对 |
| 服务商应收负责人 | 查看本方问题 → 回复或在原系统修订本方应收 | 后台发现新版并回到原对账事项；回复不能代替真实新版 |
| 服务商对接人员 | 查看候选 → 必要修订 → 查看实际试转换后确认启用 | 修订后自动安排试转换，旧生效配置继续可用 |
| 京东履约协同人员 | 查看当前阻碍 → 保存进展 → 按实际结果完成或接续 | 后台保存与恢复关联，不强制增加资料审核 |

身份、同步、重试、文件校验和模型调用均在后台执行，不计为人员日常新增操作。此为设计走查，未对真实老系统和新系统实测点击次数或效率提升。

## 3. 核心一致性与修正

- 事项完成、AI 分析、人工决定、原系统写入成功分别保存和展示；202 仅表示已受理。
- 补充接续原事项，异常关闭关联确切后续工作；不存在任意改 status 或强制对账完成入口。
- mock 数据来自模拟接口；前端只读取本系统 API，权限、计算、转换、保存和 Skill 调用按真实处理设计。
- 处理事项域补齐 INSERT 替换防护；成功补充和当前读取配置补齐 UPDATE OR REPLACE 部分唯一冲突防护。
- 同 token 续租不可换执行者；旧领取不能发布结果。新事项分析与未决指针为空，后续用受保护更新绑定。
- 输入代次独立于普通行版本，旧分析不覆盖新输入，普通进度保存不导致无限重算。
- 明细 API 与草稿保存、外部正文统一形状；数量例外和固定序列化明确。
- 费用问题组、组内问题和多次回复分别定位，同事务写 fee_verification_action；配置资料上传须唯一定位实际配置。
- 调用前通过受控接口保存 MAY_HAVE_BEEN_SENT，防止仅在收到结果后才留下调用记录。
