# delivery-planner / source-loading-order

这份文档定义执行计划写作时应该优先读取哪些真实资料，以及每类资料的用途。本项目 `docs/` 采用固定编号结构，上游文档按固定路径直接定位，不需要全盘搜索。

## 一、总顺序

按以下顺序读取，不要颠倒：

0. **上游文档清单确认**（SKILL.md Step 0.5 强制前置：逐项确认存在性，缺必需项进失败分支）
1. 仓库规则源
2. 当前正式计划文件组
3. PRD 导航源（`docs/05-prd/mainprd-<slug>.md`）
4. 任务相关子 PRD（`docs/05-prd/NN-subprd-*.md`，按任务选读）
5. Foundation 文档（`docs/03-foundation/`）
6. 真实代码与 SQL（`code/`）
7. 测试与验证资产（`docs/06-testcase/`）

核心原则：**先清单，后规则；先目标态，后现状；先 mainprd，后局部细节。**

## 二、仓库规则源

| 资料 | 用途 |
|---|---|
| `AGENTS.md` | 确认项目结构、已登记规则与 skills、协作边界 |
| `rules/coding-standards/README.md` | 编码规范索引；按任务类型选 1-2 份子文档 |
| `rules/Cloudflare支持技术栈.md`（涉及 Cloudflare 时） | 确认技术栈边界与选型约束 |

没有读完这些规则前，不要开始写正式计划。

## 三、当前计划文件组

| 资料类型 | 用途 | 读取方式 |
|---|---|---|
| 主开发计划 | 当前骨架、阶段索引、发布闸门、风险与反向索引 | 默认优先 |
| 任务看板 | 当前 Task 状态、依赖和子开发计划入口 | 按当前任务定位 |
| 子开发计划 | 当前 Task 的 PRD、核心逻辑、核心文件和验证方法 | 按 Task 读取 |
| 用户点名的计划文件 | 当前任务的直接依据 | 必读 |

如果是"更新计划"，必须读正式计划文件组，而不是只看聊天摘要。

## 四、PRD 导航源

| 资料 | 用途 |
|---|---|
| `docs/05-prd/mainprd-<slug>.md` | 建立全局地图：产品定位、系统架构、功能块索引表、各子 PRD 章节速查大纲 |

PRD 导航文档是第一层入口。先读主 PRD 的功能块索引表建立地图，再按任务进入子 PRD。

> 如果主 PRD 不存在，进入失败分支，不要继续读取其他资料。

## 五、任务相关子 PRD 源

`docs/05-prd/NN-subprd-<功能块>.md` 按功能块组织。按任务类型补读相关块，不整包读取。

| 任务类型 | 优先补读 |
|---|---|
| 接口 / 聚合服务 / DTO 契约 | `03-foundation/03-06-provided-apis/` + 对应功能块子 PRD |
| 数据库 / 配置表 / 枚举口径 | `03-foundation/03-05-schema/` + 对应功能块子 PRD |
| 外部系统对接 | `03-foundation/03-02-external-apis/` + 对应功能块子 PRD |
| 术语统一 / 文案口径 | `03-foundation/03-01-glossary/` |
| 某功能块的完整任务拆解 | 对应功能块子 PRD 全文 |

读取原则：
- 只读与当前任务有关的章节
- 大文件按章节号定位
- 章节信息最终要回写到 Task 的 `PRD 双链·读`

## 六、Foundation 文档源

`docs/03-foundation/` 的七类技术文档是确定完成标准的核心依据：

| 子目录 | 用途 |
|---|---|
| `03-01-glossary/` | 确认统一命名口径 |
| `03-02-external-apis/` | 确认依赖的外部接口 |
| `03-03-er/` | 确认对象与关系 |
| `03-04-business-flows/` | 确认角色动作和业务分支 |
| `03-05-schema/` | 确认字段、表名、枚举值 |
| `03-06-provided-apis/` | 确认接口路径、请求/响应结构 |
| `03-07-system-flows/` | 确认系统调用顺序和失败处理 |

如果 schema / 对外接口文档均缺失，则代码类任务的 `核心文件` 和 `完成标准` 无法写实，须进入失败分支。

## 七、真实代码与 SQL 源

计划不能停留在 PRD 层，必须读 `code/` 下的真实落点。

| 来源 | 用途 |
|---|---|
| Controller / Service / Mapper / DTO | 确认服务端现状、接口结构、数据口径 |
| 页面 / 组件 / store / composables / api | 确认前端现状与页面落点 |
| schema / migration / seed SQL | 确认数据库现状、关键表、关键种子 |
| 路由 / 菜单 / 配置 API 封装 | 确认配置面入口与能力 |

如果没有读到这些真实文件，就不能把 `核心文件` 和 `完成标准` 写实。

## 八、测试与验证资产

| 来源 | 用途 |
|---|---|
| `docs/06-testcase/` 的测试用例与报告 | 补齐完成标准与回归路径 |
| 真实接口样例、查询脚本、联调命令 | 写入验证门禁或任务完成标准 |

如果任务需要"完成前验证"，但没有读任何验证资产，计划大概率会空泛。

## 九、三种常见场景的最小读取集

### 场景 A：新建一份完整计划

必须先完成 Step 0.5 上游文档清单确认，再至少读取：
- 仓库规则源（`AGENTS.md` + `rules/coding-standards/README.md`）
- `docs/05-prd/mainprd-<slug>.md` + `03-foundation` 四件套
- 当前正式计划或成熟样本计划
- 与任务相关的子 PRD（非全部）
- 至少一组真实代码 / SQL / 验证资产

### 场景 B：更新已有计划

必须先确认上游文档无重大变更，再至少读取：
- 仓库规则源
- 主开发计划、任务看板和本次涉及的子开发计划
- 原计划中涉及的 PRD 双链条目
- 本次变更涉及的真实文件或验证资产

### 场景 C：只补一个 Phase

上游清单可以不整包重确认，但至少读取：
- 仓库规则源
- 主开发计划中该 Phase 前后的上下文
- 该 Phase 关联的 PRD 章节（按固定路径定位，不整包读）
- 受影响的任务看板、子开发计划、风险、闸门、索引章节

## 十、文件命名约定

以下命名约定来自本项目 `docs/` 各目录的 README，Step 0.5 按这些路径逐项确认：

| 文件类型 | 命名模式 | 优先级 |
|---------|----------|--------|
| BRD | `docs/01-brd/BRD-<项目名>.md` | 中 |
| mainprd | `docs/05-prd/mainprd-<slug>.md` | 最高，必读 |
| 子 PRD | `docs/05-prd/NN-subprd-<功能块>.md` | 按任务需要 |
| 术语表 | `docs/03-foundation/03-01-glossary/` | 中 |
| 外部接口 | `docs/03-foundation/03-02-external-apis/` | 按任务需要 |
| Schema | `docs/03-foundation/03-05-schema/` | 高，必需 |
| 对外接口 | `docs/03-foundation/03-06-provided-apis/` | 高，必需 |
| 测试资产 | `docs/06-testcase/`（`tc-main-<slug>.md` 入口） | 按任务需要 |

> **slug** 为项目英文短名（全小写、连字符分隔），与 `docs/05-prd/mainprd-<slug>.md` 保持一致；开发计划文件组必须使用同一个 slug。

## 十一、禁止行为

- 禁止在 Step 0.5 上游文档清单确认完成前开始任何写计划动作
- 禁止一次性读取整个 PRD 目录
- 禁止只靠聊天摘要写任务
- 禁止只读 PRD 不读代码就写 `核心文件`
- 禁止只读代码不回到 PRD 就写 `完成标准`
- 禁止补计划状态时只改一处，不同步回写任务看板、子开发计划和关联章节
- 禁止对大文件整包拉入上下文
